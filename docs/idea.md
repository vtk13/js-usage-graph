# Техническое описание проекта

## 1. Назначение системы

Система предназначена для помощи разработчику в понимании, анализе и изменении больших программных систем.

Основная задача системы — уменьшить когнитивную нагрузку при работе с кодовой базой, где для выполнения одной задачи требуется согласованно изменить несколько связанных участков кода.

Система должна позволять:

```text
- строить локальную модель части системы под конкретную задачу;
- видеть связи между функциями и данными;
- отслеживать поток данных между функциями;
- сохранять важные элементы кода как смысловые узлы;
- строить разные графы-представления поверх общей базы узлов;
- использовать ранее сохраненные узлы при решении новых задач.
```

Система не предназначена для построения одного полного графа всей кодовой базы как основной рабочей модели. Полный граф проекта слишком сложен и по уровню сложности может приближаться к самой кодовой базе.

Основной рабочий сценарий — построение графа, релевантного конкретной задаче.

---

# 2. Общая архитектура

Система состоит из нескольких уровней:

```text
1. Автоматический низкоуровневый граф кода.
2. База сохраненных смысловых узлов.
3. Базовые связи между узлами.
4. Пользовательские графы под конкретные задачи.
5. Слой изменений для моделирования альтернативных решений.
```

Общая схема:

```text
Исходный код
    ↓
Babel / статический анализатор
    ↓
Автоматический низкоуровневый граф
    ↓
Выбор важных узлов пользователем
    ↓
Смысловая база узлов
    ↓
Графы задач / слой изменений
```

---

# 3. Автоматический низкоуровневый граф

Автоматический граф строится на основе исходного кода.

Для JavaScript-кода предполагается использование Babel или аналогичного AST-анализатора.

Автоматический анализатор должен извлекать:

```text
- функции;
- аргументы функций;
- локальные слоты данных;
- обращения к полям объектов;
- вызовы других функций;
- передачу данных между функциями;
- простые связи между слотами данных.
```

Например, для кода:

```js
function A(user) {
    B(user.x)
    C(user.y)
    D(user)
}
```

анализатор должен построить структуру, содержащую:

```text
- функцию A;
- функцию B;
- функцию C;
- функцию D;
- слот A.user;
- слот A.user.x;
- слот A.user.y;
- слот B.x;
- слот C.y;
- слот D.user;
- связь A.user.x → B.x;
- связь A.user.y → C.y;
- связь A.user → D.user.
```

Автоматический граф является низкоуровневым техническим представлением. Он не является основной смысловой моделью системы, а используется как источник данных для навигации и выбора важных узлов.

---

# 4. Смысловая база узлов

Пользователь может выбирать узлы из автоматического графа и сохранять их в отдельную смысловую базу.

Сохраненный узел представляет не просто строку кода, а некоторый устойчивый смысл, выраженный в коде.

Ссылка на код является атрибутом узла, но не его идентификатором.

Пример сохраненного узла:

```js
{
  uuid: "semantic-node-uuid",
  name: "A",
  codeAnchor: {
    file: "src/example.js",
    functionName: "A"
  },
  slots: [...],
  links: [...],
  description: "Описание смысловой роли функции",
  notes: []
}
```

Смысловая база узлов используется повторно при решении новых задач.

Предполагается, что на ранних этапах работы с проектом пользователь будет чаще создавать и описывать новые узлы. По мере наполнения базы основной процесс будет смещаться к поиску, выбору и переиспользованию уже существующих узлов.

---

# 5. Узлы и графы

Система разделяет понятия узла и графа.

Узлы хранятся отдельно и могут переиспользоваться в разных графах.

Граф не владеет узлами, а только ссылается на них.

Это позволяет:

```text
- не дублировать описание одного и того же элемента;
- использовать один узел в разных задачах;
- строить разные представления поверх одной базы;
- отделять смысловое описание узла от конкретной визуализации.
```

Пример:

```text
Один и тот же узел может участвовать в:
- графе вызовов;
- графе потока данных;
- графе конкретной задачи;
```

---

# 6. Пользовательские графы

Для анализа системы могут использоваться разные пользовательские графы. Пользовательские графы — это представление части базы узлов под определенным углом наиболее подходящем для конкретной задачи.

---

# 7. Модель функций и данных

На начальном этапе система рассматривает две основные сущности:

```text
1. Функции.
2. Данные, проходящие через функции в runtime.
```

Функция:

```text
- принимает данные;
- обращается к частям данных;
- вызывает другие функции;
- передает данные другим функциям;
- может возвращать данные.
```

Данные внутри функции моделируются через слоты.

---

# 8. Слоты

Слот — это локальное место данных внутри функции.

Например, для функции:

```js
function A(user) {
    B(user.x)
    C(user.y)
    D(user)
}
```

у функции `A` есть слот `user`, а также подслоты `x` и `y`, являющиеся свойствами `user`.

Пример структуры:

```js
const nodes = [
  {
    uuid: 1,
    name: "A",
    slots: [
      { uuid: 5, name: "user" },
      { uuid: 9, name: "x", propOf: 5 },
      { uuid: 10, name: "y", propOf: 5 }
    ]
  },
  {
    uuid: 2,
    name: "B",
    slots: [
      { uuid: 6, name: "x" }
    ]
  },
  {
    uuid: 3,
    name: "C",
    slots: [
      { uuid: 7, name: "y" }
    ]
  },
  {
    uuid: 4,
    name: "D",
    slots: [
      { uuid: 8, name: "user" }
    ]
  }
]
```

В этой модели:

```text
5  = A.user
9  = A.user.x
10 = A.user.y
6  = B.x
7  = C.y
8  = D.user
```

Поле `propOf` задает иерархию данных.

Например:

```text
A.user
  ├── A.user.x
  └── A.user.y
```

Для более глубокой вложенности используется тот же механизм:

```text
A.user.profile.email
```

может быть представлено как:

```text
email propOf profile
profile propOf user
```

# 9. Links

Связи хранятся отдельно от узлов.

Минимальная форма — пара UUID **слотов** (источник и приёмник):

```js
const links = [
  [9, 6],
  [10, 7],
  [5, 8]
]
```

Расширенная запись: третий элемент — объект **`info`** (произвольные поля; в прототипе используются **`file`** и **`line`** — путь к файлу и номер строки в нём).

```js
[9, 6, { file: "path/to/file.js", line: 42 }]
```

Дополнительно поддерживается связь **вызова между функциями** (узел–узел): оба UUID в паре относятся к **узлам-функциям** из `nodes`, а не к слотам. Такая связь задаёт ребро «вызов» между двумя функциями; в UI оно может сливаться с ребром, построенным из слот-связей между теми же функциями. Для перехода к месту вызова в коде используется **`info`** именно у связей узел–узел (в прототипе — по клику на объединённое ребро).

Связи между слотами по-прежнему описываются парой UUID слотов; иерархия полей по-прежнему в слотах через `propOf`, не в `link`.

Для примера:

```js
function A(user) {
    B(user.x)
    C(user.y)
    D(user)
}
```

связи означают:

```text
[9, 6]   A.user.x → B.x
[10, 7]  A.user.y → C.y
[5, 8]   A.user   → D.user
```

Таким образом, слот-связь связывает конкретный слот-источник с конкретным слотом-приёмником.

Информация о том, что `x` является полем `user`, хранится не в `link`, а в описании слота через `propOf`.

В прототипе графа (`GraphExperiment`) у узла-функции ссылка на код задаётся как **`code: { file, line }`** (аналогично по смыслу `codeAnchor` в смысловой базе, см. §4).

---

# 10. Базовый граф

Базовый граф — это набор автоматически или полуавтоматически полученных связей между узлами и слотами.

Он используется для навигации по коду и выбора релевантных элементов.

Базовый граф может содержать:

```text
- связи вызова функций;
- связи передачи данных;
- связи между объектом и его полями;
- связи чтения/записи данных;
- связи с внешними сущностями, например Mongo-коллекциями.
```

Базовый граф может быть построен автоматически с помощью Babel для одного файла и дополнительно расширяться через анализ смежных файлов, подключенных через `require` или `import`.

---

# 11. Рабочий сценарий

Типичный сценарий работы системы:

```text
1. Пользователь начинает с точки входа в задачу.
2. Система строит или показывает автоматический граф вокруг этой точки.
3. Пользователь видит функции, слоты и связи.
4. Пользователь выбирает важные узлы.
5. Выбранные узлы сохраняются в смысловую базу.
6. К сохраненным узлам добавляются описания, заметки и смысловая информация.
7. Для конкретной задачи создается один или несколько пользовательских графов.
8. В пользовательские графы добавляются релевантные узлы из базы.
9. При необходимости строится слой изменений.
```

---

# 12. Слой изменений

Слой изменений используется для моделирования будущего или альтернативного состояния системы.

Он может содержать:

```text
- новые узлы;
- новые связи;
- измененные связи;
- замену старых узлов новыми;
- удаление устаревших элементов;
- альтернативную структуру потока данных.
```

Слой изменений может быть использован, когда нужно спроектировать изменение перед внесением его в код.

Если изменение простое, слой может быть объединен с основной моделью.

Если изменение связано с серьезной сменой модели данных или архитектуры, старые узлы могут быть удалены или заменены новыми без прямого слияния графов.

---

# 13. Назначение автоматического графа

Автоматический граф не должен заменять смысловую модель.

Его назначение:

```text
- быстро показать структуру вокруг выбранного участка кода;
- помочь найти соседние функции;
- показать, какие данные куда передаются;
- помочь выбрать узлы для сохранения;
- уменьшить количество ручной работы при наполнении базы;
- предоставить технические связи для дальнейшего анализа.
```

Иными словами:

```text
Автоматический граф = техническое сырье.
Смысловая база = выбранные и осмысленные элементы.
Граф задачи = рабочая модель под конкретную задачу.
```

# 14. Ключевые принципы

## 14.1. Не строить один глобальный смысловой граф всей системы

Полный граф всей кодовой базы слишком сложен и может стать не проще самого кода.

Рабочей единицей должен быть граф конкретной задачи.

## 14.2. Отделять узлы от графов

Узлы должны храниться отдельно и переиспользоваться в разных графах.

## 14.3. Автоматически извлекать низкоуровневые связи

Система должна использовать статический анализ кода для автоматического построения базового графа.

## 14.4. Сохранять только важные узлы

Не весь автоматический граф должен попадать в смысловую базу. Пользователь выбирает только те узлы, которые имеют значение для понимания системы.

## 14.5. Разделять поток вызовов и поток данных

Факт вызова функции и факт передачи конкретного поля данных — разные вещи.

Например:

```js
function A(user) {
    B(user.x)
    C(user.y)
    D(user)
}
```

Граф вызовов:

```text
A → B
A → C
A → D
```

Поток данных для `user.x`:

```text
A.user.x → B.x
```

Поток данных для `user.y`:

```text
A.user.y → C.y
```

# 15. Минимальная модель данных

Минимальная модель может состоять из трех основных структур:

```text
nodes
slots
links   // форматы — §9 (в т.ч. опциональный info и связь вызова узел–узел)
```

Пример:

```js
const nodes = [
  {
    uuid: 1,
    name: "A",
    slots: [
      { uuid: 5, name: "user" },
      { uuid: 9, name: "x", propOf: 5 },
      { uuid: 10, name: "y", propOf: 5 }
    ]
  },
  {
    uuid: 2,
    name: "B",
    slots: [
      { uuid: 6, name: "x" }
    ]
  },
  {
    uuid: 3,
    name: "C",
    slots: [
      { uuid: 7, name: "y" }
    ]
  },
  {
    uuid: 4,
    name: "D",
    slots: [
      { uuid: 8, name: "user" }
    ]
  }
]

const links = [
  [9, 6],
  [10, 7],
  [5, 8]
]
```

Эта структура позволяет восстановить:

```text
- какие функции существуют;
- какие слоты есть у каждой функции;
- какие поля принадлежат каким объектам;
- какие данные передаются между функциями;
- как построить граф вызовов;
- как построить граф потока конкретного поля.
```

# 16. Итоговая формулировка проекта

Система представляет собой инструмент для построения и поддержки рабочей ментальной модели программной системы.

Она автоматически извлекает из кода низкоуровневый граф функций, слотов данных и связей между ними. Пользователь выбирает из этого графа значимые элементы и сохраняет их в смысловую базу. Поверх сохраненной базы строятся пользовательские графы, релевантные конкретным задачам.

Главная цель системы — не визуализировать всю кодовую базу, а помочь разработчику удерживать в фокусе только те части системы, которые важны для текущей задачи, при этом сохраняя связи с уже изученными и описанными элементами проекта.
